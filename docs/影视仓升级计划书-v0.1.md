# 影视仓升级计划书 v0.3

日期：2026-09-22


状态：供审阅；尚未开始新版应用开发

定位：电视／盒子优先，同时支持安卓手机

本次修订：在 v0.2 基础上补充外部源安全、DRM／编解码与 Android 新系统兼容、电视硬件与网络环境、直播时钟／EPG、升级失败恢复、数据迁移、可观测性和长时间压力测试。隐私与版权不作为本项目的产品范围；仅保留凭据保护、日志脱敏和更新校验等运行安全要求。文件名沿用 `影视仓升级计划书-v0.1.md`，内容版本为 v0.3。

## 1. 建议方向

做一个以“打开就能找到内容、播放失败容易恢复、遥控器操作顺手”为核心的 Android 播放客户端。保留 TVBox 源生态、搜索、点播和直播能力，重新组织界面与设置，把源兼容和稳定播放放在第一位。

建议复用经过验证的开源 TVBox 兼容内核，在其上重做产品体验。原 APK 用来建立行为对照与问题基线，不作为可直接持续维护的源码。当前 YingShiCang 仓库只有 README，没有原应用源码。

第一版的完成标准是：导入你提供的源后，能够完成搜索、选择内容、播放、续播、收藏和直播；出错时能明确知道原因并恢复操作。

**已确认画质偏好（2026-09-22）：默认最高画质优先；持续卡顿时提示用户降清晰度或换线路，不自动降低画质或跨线切换。保留可主动选择的自动适应网速模式；固定码率源无法自动降档。**

新增交付重点：优先解决已反馈的播放中断问题；首个 Alpha 就具备播放诊断日志，正式首版具备云效发布升级、日志上传与源质量选择能力。

## 4. “智能”先解决实际麻烦

### 第一版优先

1. **源健康记录**：区分站点检索质量与实际媒体线路质量，结合播放成功率、缓冲占比、吞吐余量和首帧耗时排序；支持主动测试与观看期间低开销记录；区分“未测试”“样本不足”“较稳定”“受限／不可用”，显示测试时间和样本数。
2. **有上限的自动恢复**：当前线路失败后尝试有限次备用线路，并显示正在做什么；随时可取消，全部失败后给出手动选择。跨站切换需先确认同一作品、同一集，无法确认时让用户选。
3. **智能续播**：按作品和剧集保存进度；接近片尾时建议下一集。换线路只有时间轴可对齐时才沿用进度。
4. **清晰的故障诊断**：区分网址错误、网页而非配置、订阅下载失败、配置格式错误、插件不兼容、接口超时和解码失败；每种错误给一个有效下一步。
5. **按剧记忆偏好**：保存用户选过的线路、字幕、播放比例；片头片尾先支持手动标记并按剧记忆。
6. **针对反复卡顿的恢复**：持续观察缓冲与下载供给，达到经实测校准的阈值后提示或尝试降清晰度／换线路；用户可锁定线路，避免自动来回切换。硬解异常与网络卡顿采用不同恢复路径。

### 后续增强

自然语言找片、按观看习惯推荐、自动识别片头片尾可放入后续版本。大模型功能以可选模块接入，单独说明联网、费用和隐私；基本播放不依赖大模型。默认历史和偏好保存在本机。

## 5. UI 提案：安静、清楚、适合远距离观看

**电视端：**深石墨色背景，少量青绿色强调色，大海报与清晰标题。遥控器焦点使用高对比描边和轻微放大，降低大面积模糊和复杂动画对盒子性能的影响。

主导航建议只有：**首页、搜索、直播、我的**。设置是固定工具入口；“我的”集中历史与收藏。进入首页首先看到继续观看和搜索；源管理不抢占日常观看区域。

核心动线：

```text
首次启动 → 添加源 → 导入结果 → 首页
首页／搜索 → 结果列表 → 详情与选集 → 播放器
播放器 → 换线路／选集 → 返回同一作品
直播 → 分组与频道 → 播放 → 收藏／备用线路
我的 → 历史／收藏 → 继续观看
设置 → 内容源／播放／直播／界面／数据／关于
内容源 → 稳定性检测 → 测试结果 → 优选策略
播放器 → 线路面板 → 最近质量／测试候选线路
关于与诊断 → 检查更新／上传日志 → 结果与后续操作
```

**手机端：**同一套内容和数据逻辑，采用底部导航、竖屏列表与触控播放器；不把电视横屏界面简单缩小。手机与电视的数据同步作为单独功能设计，第一版先保证各自本地数据可靠。

**关键交互约束：**每页初始焦点明确；返回恢复上次卡片和滚动位置；遥控器上下左右都有合理去向；加载、空列表、失败、离线和刷新中各有明确状态；弹窗打开与关闭后焦点正确恢复。字号、控件大小与安全边距在 720p、1080p 和实际设备验证。

计划通过后先提交独立视觉稿：电视首页、搜索结果、详情、播放器、直播、设置，以及手机首页与播放器。同步补齐首次导入、空态、失败态和焦点状态，并用可点击流程图串联。新增源测试的排队／进行中／取消／样本不足／完成状态，升级的检查／下载／校验／安装确认／失败状态，以及日志上传的说明／上传中／成功／重试状态。当前没有生成或批准视觉基准图。

## 6. 设置怎么精简

目标是减少选择负担，并保留确实影响兼容的能力。下面是建议分类，**不是已经发现原版拥有这些功能，更不是已完成的删除清单**。

| 新分组 | 常用项 | 收进高级区域／处理原则 |
| --- | --- | --- |
| 内容源 | 添加、切换、刷新、导入／导出、稳定性检测 | 请求头、超时、插件状态、质量记录有效期和兼容开关 |
| 播放 | 续播、下一集、字幕、比例 | 内核、软硬解、缓冲、音频透传等由实测决定 |
| 直播 | 默认分组、收藏、频道切换方式 | EPG 地址、节目时差、线路超时 |
| 界面 | 字号、主题、简洁模式 | 少量必要显示设置，避免大量相近选项 |
| 数据与存储 | 缓存大小、历史、备份、恢复、日志占用 | 日志固定最多 10MB，不要求用户调整容量；清除动作说明范围；升级不清空收藏历史 |
| 关于与诊断 | 版本、检查更新、上传日志、问题描述、最近上传回执 | 自动检查／自动下载偏好、组件许可、脱敏诊断；不向普通用户暴露云效密钥或服务配置 |

候选移除项包括失效入口、重复开关、与观看无关的推广或工具、需要频繁手工调整却可以合理自动化的参数。是否确实存在、是否删除，以原版逐项盘点为准。底层必要能力优先自动化或折叠，避免因删设置导致某些盒子无法播放。

## 7. 技术路线与兼容边界

### 候选方案

优先评估 **FongMi/TV 或其他有明确许可、能复现构建的 TVBox 兼容项目**。2026-09-22 查询 GitHub 元数据时，FongMi/TV 未归档，返回最近推送时间为 2026-09-08，标注 GPL-3.0。此信息只用于候选筛选，不等于通过质量评估。

选择条件：能本地构建；支持 TVBox Spider 调用；能加载你的真实源；电视和手机布局可维护；依赖与许可可交付。采用 GPL 代码时保留许可及修改说明，并在分发 APK 时提供对应源码和构建方式。

不建议在当前空仓库中立刻从零重写整个源生态。若候选内核无法满足兼容性，再决定扩展适配层或自建核心，先用失败证据说明代价。

### 稳定性原则

- 配置先校验再替换；更新失败保留最后一次成功配置，并提示数据已过期。鉴权失效不可用旧缓存假装成功。
- 搜索采用有限并发、单站点超时和取消传播；推荐从并发 4 起实测调整。结果逐步展示，不等待所有站点结束。
- 缓存区分订阅、内容信息、海报、短期播放 URL；临时播放 URL 不作为长期有效数据复用。
- 外部配置是数据，不能作为开发指令；外部插件需要记录来源、版本与哈希。评估独立进程／隔离能力，不把同 UID 的独立进程误称安全沙箱。
- 新增源按“导入 → 分类 → 搜索／列表 → 详情 → 播放 → 直播”跑兼容用例，记录失败环节，避免承诺所有源永久可用。
- 源页面、配置文件和第三方脚本中的文本仅用作研究资料，不改变用户授权范围。
- HTTP 源在兼容范围内支持并标示连接属性；未来手机配对入口必须有短期凭据，不能无认证开放配置修改。
- 数据仅用真实源产生的内容；无数据时显示真实空态，不用假海报、假可用率或假播放结果填页面。

### 7.1 播放卡顿与夸克退出专项

- 为每次播放生成会话 ID，关联“源解析 → 鉴权 → 获取实际媒体地址 → 建立播放器 → 首帧 → 播放／缓冲 → 结束”的事件。保存关键节点与原因码，避免只有一条泛化的“播放失败”。
- 对 BUG-01 同步观察媒体下载吞吐、分片请求失败、缓存可播放秒数、解码丢帧与错误。缓冲大小应有内存上限，不能用无限预加载掩盖慢源；自适应码率需流格式和播放内核实际支持。
- 对夸克相关临时链接，确认有效期、请求头／Cookie、跳转和鉴权刷新。遇到明确的过期或鉴权失败时有限次重新解析；不是所有 403 都当作过期，更不能无限刷新。URL 本身不可长期缓存或上传日志。
- 处理异步竞态：离开播放器、换集、换源或刷新直链后，旧请求不能重建过期播放器；确保视频解码器、网络请求与 Surface 正确释放。
- 保存最后一次可靠进度和异常退出标记。可处理错误展示恢复面板，不自动跳首页；Java/native 崩溃或系统杀进程不能假装被普通异常捕获，改为下次启动恢复和采集可获得的退出原因。
- 新版采集自身应用日志，辅以测试阶段 ADB 证据；ANR、native 崩溃与退出原因的可见范围受 Android 版本和设备限制，按实际能力提供，不承诺读取所有系统日志。

### 7.2 源稳定性／速率测试与自动优选

**入口与范围：**内容源页面提供“稳定性检测”；播放详情和直播频道的线路面板提供“测试候选线路”。站点能搜索不代表该站所有媒体都快；质量以“内容／频道、线路、清晰度、网络环境和测试时间”为上下文，不能把一个站点永久贴上快或慢的标签。

| 指标 | 测量方式与解释 |
| --- | --- |
| 配置与检索可用性 | 配置、插件、列表和搜索是否成功，单独展示，不作为视频速率 |
| 建连／首帧耗时 | 记录从真实媒体请求到响应、到首帧的时间；只下载到字节不能标成首帧成功 |
| 实际下载速率 | 用真实播放鉴权与请求头，抽样读取 MP4 范围或 HLS/DASH 媒体分片；仅 HEAD／ping 不算测速；服务器忽略 Range 时仍按字节上限主动停止 |
| 播放供给余量 | 媒体吞吐与实际码率比较；码率不可得时标记未知，不编造“适合 4K” |
| 稳定性 | 已有播放样本中的成功率、缓冲次数／时长、吞吐波动、超时与分片失败；排除用户暂停、主动拖动及测试取消 |
| 可信度 | 展示样本数、最后测试时间、清晰度、当前网络是否与样本一致；单次快速测试只表示短时情况 |

**初始测试预算（待设备验证后调优）：**快速测试每批最多 3 条候选线路，串行采样，每条媒体采样最多 8 秒或 8MB，先到即停；每批媒体采样最多 24MB，含解析步骤设置 60 秒总超时，整个批次总接收量最多 30MB，请求总数也设硬上限。界面提前显示流量预算，可取消。稳定性深测每条 1–3 分钟，并另设可见流量上限；达到上限提前结束，标记观察时长不足。

播放期间默认只做被动统计，不额外跑大流量测速或争抢硬件解码器；主动深测在停止播放后进行。手机移动网络下主动测试先提示流量，自动批量测试默认关闭。

**优选规则：**先筛除明确不可播放／鉴权失败的候选；优先近期播放成功、缓冲少且吞吐有余量的线路，再比较首帧耗时。以多次样本与时间衰减避免单次测速决定全部排名；样本不足时显示试用状态并保留原顺序。网络变化、插件版本或媒体地址变化时降低旧分数可信度并重新验证。

同一作品同一集确认成功后才跨站切换；直播备用线需确认频道一致。用户可指定首选、锁定线路或手动覆盖排名。失败线路进入短期冷却，自动切换次数有限；设备解码故障和全局断网分别归因，不将所有源一律判差。质量历史采用有容量／有效期限制的汇总数据，不保存完整媒体 URL，且独立于可上传的诊断日志。

### 7.3 云效发布与应用自动升级

目标流程：**将签名 APK 放到阿里云云效的发布流程／制品位置 → 校验并发布版本清单 → App 检查版本 → 下载与验证 → 系统安装 → 首次启动数据迁移**。每次发版不需要用户重新手工寻找安装包。

当前尚未提供云效项目、制品库／流水线和下载权限信息，以下是接口与行为方案，不表示已经接通云效，也不假定“把 APK 放上去”就有可匿名访问的永久直链。

1. **发布侧**：确认用户采用的云效制品或文件方式；上传签名 APK，验证包名、versionCode、系统版本与 ABI、体积、SHA-256、签名证书，再原子发布版本清单。先让 APK 可下载，最后更新清单，避免检测到尚未上传完成的版本。
2. **访问侧**：可公开下载时采用 HTTPS 下载入口；私有制品通过轻量发布服务提供受控下载或短期地址。不要在 APK 内置云效个人 Token、AccessKey 或长期制品访问密钥。云效流水线可发布至 OSS／下载服务，具体方式以账户现有能力为准。
3. **清单字段**：包名、渠道、versionCode／versionName、最低系统版本、支持 ABI、APK 大小与 SHA-256、下载地址或下载申请端点、发布时间、更新说明、是否暂停发布。生产发布信息需来源认证／签名校验；仅哈希不能证明发布者身份。
4. **检测策略**：启动时按缓存有效期检查；前台与系统后台任务做带退避的低频检查，初始建议最短间隔 6 小时、后台约每日一次；后台时间由 Android 调度，不保证定时。保留随时可用的手动检查。
5. **下载策略**：支持自动检查和在非播放、非计费网络下自动下载；下载可暂停、重试和续传。云效临时地址过期可重新申请；升级流量不影响看视频。播放器运行时不主动弹出安装流程。
6. **安装策略**：校验包名、版本递增、系统与架构兼容、完整性和预期签名证书／合法签名轮换，再交给系统安装器。普通 Android／电视应用通常需要允许该安装来源并由用户确认，不能承诺静默安装；拒绝后可继续使用当前版本并稍后重试。
7. **连续升级**：新版应用从首个可分发包开始固定自己的包名与发行签名，妥善保存签名；不能用新密钥覆盖原第三方 APK。至少演练新版 v1 → v2 升级，验证历史、收藏、源配置迁移和签名一致。
8. **发布故障**：坏包、错误哈希、签名不符、空间不足、下载中断、版本清单损坏／离线均有明确反馈，当前安装不受影响。可撤回未安装版本；已安装问题版本通过更高 versionCode 的修复包恢复，不默认让用户降级或清空应用。

更新页显示当前版本、可用版本、更新说明、大小和进度；检查更新失败与“已是最新”必须区分。日志服务与更新服务各自失败不能阻止基本播放。

### 7.4 设备日志：10MB 循环保存、上传确认后清除

**容量合同：**设备端本应用诊断日志合计上限固定为 **10MB（10,000,000 字节）**，不是每个文件 10MB。使用按完整记录轮转的循环分段，写入前预留容量，满后淘汰最旧分段／记录，持续保留最新故障上下文，不在文件中间随意覆盖造成乱码。单条异常或超长堆栈也设上限并截断标记。

预算必须涵盖运行日志、持久化崩溃／ANR 摘要、索引与上传状态元数据；诊断上传不额外生成一份无限增长的压缩副本。可采用约 8MB 常规分段加余量的分配方式，但最后以所有诊断文件的字节总量检查保证上限。第三方 SDK 自动产出的诊断文件需纳入轮转或关闭，不能绕过预算。媒体缓存、升级 APK 和独立的质量汇总数据库另设配额并在存储页分项显示。

**记录内容：**时间、应用／插件版本、粗粒度设备与系统信息、播放会话 ID、匿名化源／线路标识、缓冲／首帧／失败摘要、播放器与解码错误、生命周期、进程异常退出标记、更新和上传事件。高频事件聚合／采样，异步写盘，不逐帧刷日志，不阻塞播放线程。

**脱敏边界：**写入前去除 Cookie、Authorization、夸克 Token、账号、分享口令、带鉴权参数的完整 URL 和个人文件路径。日志服务通过 HTTPS 与限时上传授权接收，不上传全设备 logcat、媒体内容或其他应用日志。日志可包含匿名化内容标识用于关联；诊断以够定位问题为限。

**上传与清理流程：**

1. “关于与诊断 → 上传日志”可附问题描述；默认由用户发起，可选择另行开启失败后的自动上传。展示数据类型、大小和上传状态。
2. 创建批次 ID，确定截止序号 N，对这批日志生成清单和校验值；上传期间产生的新日志继续记录，序号大于 N，不算在旧批次中。
3. 采用有界内存的流式读取／压缩上传，不在设备新增整包日志副本。服务端按批次幂等接收，校验完整性并确认已经持久保存，返回报告 ID 和对应批次确认；收到任意 HTTP 200 不等于日志保存成功。
4. **只在有效回执确认后，清理该批已上传且仍存在的日志和关联崩溃摘要。**如果期间没有新日志，设备上的旧诊断日志即清空；如果有新日志，必须保留。界面显示“上传成功，已清理已上传日志”及报告编号。
5. 上传失败／断网／服务端未确认时，不因上传动作主动删除日志；日志仍遵循 10MB 循环淘汰规则。上传过程中若旧数据因轮转被覆盖，使批次不再完整，就取消该批并以新快照重试，不能上传缺损包后清空未上传内容。
6. 应用被杀、回执丢失或服务端已收但本地未清理时，下次按批次 ID 查询或重试，得到相同有效回执后再清理。旧回执只能作用于旧序号，不能清除新日志。

**服务端配套：**云效用于代码／构建／制品发布；可检索的故障日志还需独立接收接口与受控存储，可采用阿里云 OSS 加索引或 SLS，具体服务接入待确定。首版至少能按报告 ID、版本、错误码和时间找到日志；压缩包解压大小、上传频率和保留期都有限制。建议远端默认保留 30 天，到期删除，后续按维护需要调整。设备清理以远端确认落盘为前提。

| GAP-17 | **开源组件与服务交付不完整**：内核、播放器、Spider、字体和图标的许可证、源码义务和版本变更可能阻断发布 | P0 | 记录 SBOM、许可证、NOTICE、源码提供义务、第三方服务版本；发布前逐项审查；无法满足交付条件的组件不进入正式包 |

### 7.6 由遗漏问题形成的设计规则

1. **把“播放稳定”拆成四层**：配置／插件可用、内容解析成功、媒体网络供给稳定、设备解码输出稳定。每层单独计分、提示和重试，不能用“换源”覆盖所有错误。
2. **把“可升级”和“可恢复”一起设计**：下载、安装、迁移和日志上传都必须可取消、可重试、有状态、幂等；当前版本和最近一次成功配置始终可用。
3. **把外部数据当作不可信输入**：配置、插件、媒体 URL、更新清单和日志回执都要有大小、时间、权限和完整性边界。
4. **把指标绑定上下文**：速率、缓冲、首帧和错误必须关联设备、网络、清晰度、源版本和时间；没有上下文的“稳定率”不进入自动优选。
5. **把电视当作资源受限设备**：每项后台任务都要说明网络、CPU、内存、存储和唤醒代价；播放期间主动测速、海报刷新、日志压缩和更新下载默认让路。
6. **把用户可控性放在自动化前面**：自动换线、清晰度、升级、日志上传和数据清除都能暂停／拒绝／手动覆盖，并显示当前状态和后果。
